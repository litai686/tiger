# Agent 设置与云端模型（桌面端）

> 范围：`config.json` 里的 Agent 设置项、推理强度与思考开关的映射、云端模型 `can_reason` 约定，以及写入 tigerAgent.json 的开关链路（`/config/set` + `/agent/update`）。

---

## 设置项与开关写入链路

- **Agent 设置**：`agent_default_provider` / `agent_thinking_enabled` / `agent_reasoning_effort` / `agent_temperature` / `debug_logging` / `agent_allow_all_tools` 存储在 `config.json`（Settings 结构体），前端通过 `load_settings` / `save_settings` 读写。设置面板把思考开关与推理强度**合并为一个「推理强度」下拉**（`关闭 / low / medium / high`）：选「关闭」= `agent_thinking_enabled=false` → 发 `reasoning_effort: none`（保留原档位，切回具体强度即恢复），其余档位为 `agent_thinking_enabled=true` + 对应 effort；转换在 `utils.js` 的 `reasoningSettingValue` / `applyReasoningSetting`。桌面端与 Agent 均固定 yolo（执行）模式：没有任何 Plan 模式开关，`/v1/workspaces/{id}/agent/mode` 端点已随 Plan 模式一并移除（**breaking change**：更早版本的 TUI 或第三方客户端调用该端点会收到 404，旧 TUI 的 `ctrl+y` 表现为静默无效；仓库内调用方仅 TUI `workspace/client_workspace.go`，已同步更新）。
- **云端模型管理已迁到独立底部 TAB「模型管理」**（`src/views/models.js`，路由 `#/models`，位于 Agent 右侧）：provider 列表 + 添加/修改/删除都在这个视图内；Agent 设置弹窗（`src/views/agent/settings_dialog.js`）只保留推理强度/温度/多模态模型等会话级设置，`template.js` 里的 `#provider-list` 与 `agent-add-model-overlay` 已删除。模型下拉底部的「+ 添加云端模型」改为 `location.hash = "#/models"`。视图内删除确认/提示不能用 `agent/ui.js` 的 `showConfirm`/`showNotice`（挂在 `.agent-root`/聊天区，切到其它 TAB 时不可见），必须用视图内自建弹窗。
- **添加/修改云端模型弹窗的模型ID候选列表**（桌面端 `src/views/models.js`）：弹窗字段顺序为 Base URL → API Key → 模型ID → 名称（模型ID 紧跟 Key 之后）。填写 Base URL（和 Key）后 `change` 时通过 Rust `probe_models_endpoint` 请求 `{Base URL}/models`（OpenAI 兼容，`Authorization: Bearer <key>` 仅在有 key 时附带，10s 超时；**必须走 Rust**，WebView 页面源 `http://tauri.localhost` 直连会被 CORS 拦成“地址或密钥不正确”，同 `fetch_skill_store`），解析 `data[].id`（兼容直接返回数组）填充 `models-modelid` 的 datalist，模型ID 可下拉选择、也可手动填写；拉取失败（无 key / 服务商不支持）不阻断：候选清空、模型ID 仍可手动填写，且在 `#models-fetch-msg` 显示具体错误（HTTP 状态/异常）与手动填写指引；成功显示候选数量，返回空列表提示非 OpenAI 兼容。**提交时强制校验**（新增/修改均生效）：`submitModel` 先调同一命令，失败/非 OpenAI 兼容响应直接红字报错并 return，不写入 provider。同一 `base|key` 组合去重，不重复请求；并发拉取用 `modelIdFetchSeq` 序号丢弃迟到的旧响应（与 `model.js:refreshAgentInfo` 的 `agentInfoSeq` 同法）。
- **服务端内置模型不进「云端模型」管理列表**（`src-tauri/src/pages/agent.rs` 的 `cloud_providers_from_settings`）：`GET /v1/settings` 的 `providers` 会包含服务端代码注入的内置 provider `tigerAgent`（模型 `agent-models`，由服务端后端池轮询，无 base_url/api_key）。`list_cloud_providers` 与 `local` 一样把它过滤掉：内置模型只需经 `GET /v1/workspaces/{id}/providers` 快照进入模型下拉供选择，不出现在设置的可编辑/删除列表里；漏过滤会让 `send.js` 的 `getModelReadiness` 把它当成用户添加的云端 provider 并误报「缺少接口地址（Base URL）」。
- **发送前的 API Key 校验读 `has_key`，不读 `api_key`**（`send.js:getModelReadiness`）：`list_cloud_providers` 出于安全不回传密钥（`CloudProviderView.api_key` 恒为空串，`GET /v1/settings` 只回掩码），密钥是否已保存由 `has_key` 表达。校验若只看 `p.api_key` 会对所有用户添加的云端模型恒误报「缺少 API Key」。同理，`workspace.js:refreshProvidersOnSwitch` 切 workspace 后触发目标 ConfigStore 重载的幂等 `config/set` **不能写 `providers.<key>.api_key`**（`trigger.api_key` 恒为空，写空串会把服务端已保存的密钥清空——`SetConfigField` 是 sjson 原样覆盖，无「留空保留」语义），改写 `providers.<key>.name` 同样能触发 autoReload 且无破坏性。
- **添加/修改/删除云端模型即时生效，无需重启 Agent**（服务端 `backend.ApplySettings` → `reloadLiveWorkspaceConfigs`）：桌面端只走 `POST /v1/settings`（`add/update/delete_cloud_provider`），写入的是**后端全局** ConfigStore；而每个 workspace 在创建时各自 `config.Init` 出一份独立快照，`GET /workspaces/{id}/providers` 与 agent 构建模型读的都是 `ws.Cfg`，store 之间既没有文件监听也没有写入通知。服务端因此在落盘后显式对每个存活 workspace 调 `ReloadFromDisk`（并发，避免多 workspace 时串行累加超过桌面端 15s 超时），否则 `refreshServerProviders` 拿到的快照不含新 key，前端会把它标成 `pendingProviderKeys`、从模型下拉隐藏并提示「重启 Agent 后生效」。**前端同样要刷新两处数据**：`src/views/models.js` 的添加成功分支必须重新 `invoke("list_cloud_providers")` 覆盖 `S.providers`——「模型管理」列表渲染的是 `S.providers`，它只在进入 Agent 页 / 切换 workspace 时加载，漏刷新会表现为「提示添加成功，但列表里看不到」（修改/删除分支已有同样的刷新）。改这条链路时不要只测模型下拉，两个回归点都要验：添加后**当前 workspace 的模型下拉**与**「模型管理」列表**都立即出现该模型（服务端用例 `TestApplySettingsReloadsLiveWorkspaceConfig`）。
- **模型上下文窗口按新键 `ctx_size` 读取**（`src/views/agent/utils.js:modelContextWindow`）：`GET /v1/workspaces/{id}/providers` 的 `models[]` 与 `GET /v1/workspaces/{id}/agent` 的 `model` 都是服务端 `config.ModelInfo`，窗口字段序列化为 `ctx_size`（旧键 `context_window` 只作配置输入别名）。桌面端写进 tigerAgent.json 的 provider 双写两键，所以磁盘来源的旧快照仍能被旧键兜底；但服务端内存注入的内置模型 `tigerAgent/agent-models` 只有 `ctx_size`，只读旧键会让上下文显示停在 `0 / 0`（切模型后 toolbar 与状态栏都不再更新）。因此模型下拉条目、`refreshAgentInfo`、`resolveAgentModel`（切模型时传入即时窗口）一律经 `modelContextWindow` 取值：新键优先、旧键兜底、都没有才当未知（0 = 服务端未上报窗口）。
- **云端模型一律按「支持思考」写入**（桌面端 `add/edit_cloud_provider` + `src/views/models.js` 弹窗）：添加/修改云端模型的弹窗已去掉「支持思考模式」复选框，`can_reason` 恒为 `true`（同时写入 `reasoning_levels: ["low","medium","high"]` 与 `default_reasoning_effort: "medium"`，见 `src-tauri/src/pages/agent.rs:1333` / `:1553`）。**含义与边界**：`can_reason` 是能力总闸而非当轮档位——为 false 时服务端**永不**发送 `reasoning_effort`（`Agent/internal/agent/coordinator.go:386`）；为 true 只是「允许发」，发不发仍由工具栏「推理强度」决定（选「关闭」→ 前端发 `reasoning_effort: none`（`utils.js:getRequestReasoningEffort`）→ `llm/client.go:204-219` 翻译为关闭思考，思考能力照样关掉）。因此**编辑既有非思考条目会把它静默升级为支持思考**（旧配置 `can_reason=false` 无法再通过弹窗保留）：对完全不接受 reasoning 参数的厂商，唯一退路是全局「推理强度=关闭」，而该路径本身会带 `reasoning_effort: none`，可能命中 `thinking_mode_unsupported` 400 并中断本轮；弹窗内已加只读提示说明该约定。若将来要恢复「零参数」能力，改法是编辑路径保留原条目的 `can_reason`、仅新增时默认 true。
- **开启所有工具调用**（Agent 设置→基础设置，`agent_allow_all_tools`）：开启后 `settings.rs` 调 `agent.rs` `sync_agent_allow_all_tools`，把 `options.bash_allow_all` 补丁进 tigerAgent.json → `POST /config/set`（磁盘全量重载）→ `POST /agent/update`（`UpdateModels` → `buildTools` 重建工具集）。**两个请求都必需**：config/set 只换配置对象，工具集是 buildTools 时构建的，少了 agent/update 开关不生效。Agent 侧需支持 `options.bash_allow_all`（`internal/config` Options + `tools/bash.go` 的 `blockFuncs(allowAll)`），未支持的版本会静默忽略该字段（Go 不拒绝未知字段），开关表现为空转。Linux 上真正执行 sudo/apt 还需 `NOPASSWD` 免密（agent 进程无 TTY）。改动清单见 `doc/agent-patch-bash-allow-all.md`。
- **服务端日志入口**（Agent 设置→基础设置，`#settings-open-server-logs` → `#agent-server-log-overlay`）：服务端日志在服务端主机上，远程部署时本机没有该文件，因此不做“打开目录”，而是经 HTTP API 取回——`fetch_server_logs`（列表）、`fetch_server_log_text(name, tail)`（按行数查看，默认 1000 行，可选 200/1000/5000/整文件）、`download_server_log(name)`（整文件下载到本机）。前端逻辑在 `src/views/agent/server_logs.js`，Rust 转发在 `src-tauri/src/pages/logs.rs`；接口契约见 `doc/server-api.md` §1.11。注意与「打开日志目录」（`open_debug_log_dir`，只定位客户端自己的 `tigerAgent_debug.log`）区分。
- **项目记忆入口与「压缩时自动提取记忆规则」开关**（桌面端 UI + Agent `options.project_memory_sync`）：项目记忆不再放在 Agent 设置弹窗里，改由 toolbar「🧠 项目记忆」按钮（`id=agent-memory-btn`，紧邻「压缩上下文」）打开专用弹窗 `#agent-project-memory-overlay`（`src/views/agent/template.js` 标记 + `src/views/agent/memory.js` 的 `initProjectMemoryUI`/`openProjectMemoryDialog`/`refreshProjectMemory`；原 `settings_dialog.js` 里的 `initProjectMemoryUI` 已整体迁到 memory.js，`showSettings` 不再刷新记忆）。弹窗内的开关写入 config.json 的 `agent_project_memory_sync`（默认开：前端一律用 `!== false` 判定，见 `memory.js:memoryAutoExtractEnabled`；Rust 侧该字段是 `Option<bool>` + `skip_serializing_if`，**None = 未设置 = 开**——`Settings::default()` 的零值在 `save_agent_workdir` / `save_workdirs_internal` 等「首次写盘」路径里会被直接落盘，用 `bool` 会把「默认开」静默写成 `false`），`save_settings` 调 `agent.rs:sync_agent_project_memory`（`unwrap_or(true)`）→ `write_agent_option_bool("project_memory_sync", …)` 补丁 tigerAgent.json 的 `options.project_memory_sync` → `POST /config/set` → `POST /agent/update`（与 bash_allow_all 同一套流程）。Agent 侧已支持该选项（`internal/config` 的 `Options.ProjectMemorySync *bool` → `coordinator.go` 传**闭包**（读活配置）→ `internal/context/manager.go` 的 `Manager.ProjectMemorySync func() bool`（nil = 开），压缩时实时求值，为 false 时跳过 `m.Project.Sync(...)`，**只停新增、不关注入**：`ProjectRender` 不受影响）。**必须用回调而不是快照 bool**：coordinator 只在构造时 `buildAgent` 一次（`coordinator.go:209`），之后 `run()` 走 `c.currentAgent.Run`、手动压缩走 `c.currentAgent.Summarize`，而 `/agent/update`（`UpdateModels`）只做 `SetModel`/`SetTools`、从不重建 `ctxMgr`——快照写法会把开关冻结到服务重启（实测：开关写入 `false` 且 `/config/set`+`/agent/update` 均 200 后，手动压缩仍在 11ms 内改写 `project_memory.json`）。改成读活配置的闭包后，`/config/set` 的 autoReload 一刷新即对下一次压缩生效，**不需要 `/agent/update`、也不需要重启**。改动清单见 `doc/agent-patch-project-memory-sync.md`。
